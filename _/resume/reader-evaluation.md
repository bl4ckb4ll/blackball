# Reader boundaries: both PDF candidates compile; neither qualifies

## October 27 executable comparison

The earlier GHC acquisition blocker is cleared. A complete official Ubuntu
24.04 x86_64 GHC 9.14.1 distribution and Cabal 3.16.1.0 were checked against
their published SHA-256 manifests. Both unmodified source-pinned libraries
compiled, and the two thin [foreign-library clients](../../examples/autogenerated/pdf-fixtures/foreign-readers/) actually ran.
`hpdft` also built its CLI and page examples. `pdf-toolbox` qualification built
its core, content and document libraries, not its optional graphical viewer.
The resolved dependency sets and [environment receipt](pdf-qualification/environment.tsv)
are retained. This is local execution, not a hosted or clean-host acceptance.

The [contract](pdf-qualification.md) and [expected observations](fixtures/pdf/expectations.tsv)
were specified before candidate output was inspected. An independent Idriç PDF
writer produced the small ASCII-syntax PDFs; Ghostscript produced the
password-protected negative case. Original fixture bytes are committed. Both
clients ran on the same twelve files under elapsed/CPU/address-space/output/FD
limits, producing 24 captured executions. The Idriç checker imports neither
reader nor the intake. It compares exact text, page identity, geometry, image
classification and refusals, and rejects deliberately changed observations.

| Observation | hpdft | pdf-toolbox |
|---|---|---|
| Ordinary wording, both columns and two-page identity | PASS | PASS |
| Accented Latin, Greek, CJK and supplementary Unicode | FAIL: final U+1F600 becomes U+FFFD | PASS |
| Unknown named glyph without a Unicode mapping | FAIL: emits `/UnknownFixtureGlyph` as text | PASS: explicit `UNMAPPED` |
| Standard Helvetica without an explicit Widths array | FAIL: zero segment advance | FAIL: every glyph has the same x coordinate |
| Courier control with explicit 600-unit widths | PASS | PASS |
| CropBox values and 90-degree rotation retained | PASS in raw page evidence | NOT QUALIFIED by this client; MediaBox alone is exercised |
| Painted image versus blank page, including mixed documents | PASS | NOT QUALIFIED by this client |
| Malformed structure and password-protected input | Both refuse | Both refuse |

The ordinary PDF is valid: standard Helvetica may omit Widths. At 12 points
its initial `N` advances 8.664 points and the first line advances 110.04 points.
Adobe's Helvetica AFM supplies the independent widths, and Poppler's rendered
page and `-bbox` extraction independently show nonzero advance. The explicit
Courier control advances 7.2 points per glyph and passes both clients. The
missing standard-font fallback is a real geometry defect; changing the ordinary
fixture to always supply Widths would conceal it.

The Unicode fixture deliberately separates logical ToUnicode values from
visible Helvetica glyph shapes. Its explicit CMap and independent Poppler
extraction both give `Zoë Ω 中 😀`. The hpdft output contains an actual replacement
character, not merely a terminal display discrepancy. The image fixture has an
actual painted Image XObject; the blank page retains the same unused image
resource, proving that resource presence alone is insufficient classification.
The hpdft client uses interpreted image placements without decoding pixels.
Its first client unnecessarily decoded pixels and encountered an unsupported
ASCIIHexDecode filter; that client was repaired, not the fixture or library.

The captured [hpdft checks](pdf-qualification/hpdft-checks.tsv) and
[pdf-toolbox checks](pdf-qualification/toolbox-checks.tsv) both return failure
for qualification. Both reject dropped text, merged pages, shifted coordinates,
invented OCR text and zeroed advances. The supplementary-character mutation
passes its control for pdf-toolbox; for hpdft it is **BLOCKED**, because its
unmodified baseline already fails. No failed baseline is promoted to a passing
negative control.

**Selection: no production reader is qualified.** pdf-toolbox preserves more
of the required Unicode/uncertainty evidence, but selecting it for production
would still require standard-font metrics and exercised crop/rotation/image
observations. hpdft would additionally need lossless supplementary decoding and
an explicit unknown-mapping boundary. These clients are inspection programs,
not production adapters. PDF intake correctly remains `PdfReaderNotQualified`.
No Idriç source anchor or review record is constructed from these observations.

The current host refuses the namespace probe. A separate, actually compiled
Idriç Landlock ABI query returns `Function not implemented (ENOSYS, 38)`;
see [the raw query](pdf-qualification/sandbox-query.tsv). This does not prove
that every possible isolation mechanism is unavailable. A production
non-networked reader boundary is still **NOT QUALIFIED**; process resource
limits alone do not establish it. OCR was neither installed nor invoked.

The unchanged 41 intake assertions were compiled and rerun using the same Idriç
source pin, and their output matches `producer-cases.tsv` byte-for-byte.
This recheck is producer regression evidence, not independent whole-résumé
semantic acceptance or a new DOCX filesystem round trip. Production source,
existing review records and the original DOCX qualification are unchanged.

## October 25 acquisition history

The two requested upstream repositories were cloned and inspected at the
revisions in dependencies.tsv. Their actual libraries, package descriptions,
license files and relevant extraction interfaces were read. No fork was made.

| Candidate | Inspected capability | License | Executed build result | Fixture qualification |
|---|---|---|---|---|
| hpdft | PDF.Page structured extraction and PDF.Interpret geometry; layout and Unicode mapping modules | MIT | BLOCKED before compilation: GHC could not start | NOT_RUN |
| pdf-toolbox | pageExtractGlyphs returns spans with glyph positions; pageMediaBox and Unicode decoders | BSD-3-Clause, per package LICENSE files | BLOCKED before compilation: GHC could not start | NOT_RUN |

hpdft's pinned package requires base >=4.18; its README requests GHC 9.14+.
The observed Ubuntu package candidate GHC 9.4.7 provides base 4.17.2.0 and
cannot satisfy that package. This is not evidence of an upstream compiler bug.

No GHC or Cabal was initially installed. Cabal 3.8.1.0 was acquired into the
disposable workspace. A GHC acquisition attempt returned a truncated archive:
51,802,962 bytes instead of the package index's 78,997,210 bytes. dpkg-deb failed
with unexpected end of file; the partial GHC then failed to load
libHShaskeline-0.8.2-ghc9.4.7.so. Both actual `cabal build --offline` invocations
failed before determining a usable compiler version. No candidate is declared
unbuildable upstream, and no Unicode/layout behavior is inferred from its README.

The isolated-process prerequisite was also probed with
`unshare --user --map-root-user --net true`. The host refused writing uid_map
with “Operation not permitted.” An available network/process isolation boundary
has not been established. Resource limits alone do not establish isolation.

The earlier compiler and namespace failures remain evidence about the PDF
candidate build path. They do not block the already installed Pandoc executable.
DOCX now executes through Pandoc 3.1.3+ds-2, pinned by binary digest and upstream
source revision. The Idriç ZIP/XML sidecar checks bounds, preserves original Word
parts and constructs actual part/paragraph anchors. Ordinary, Unicode, table,
header and academic footnote fixtures complete intake/review/reload. Encrypted
ZIPs, oversized expansion, XML entity declarations, external resource
relationships, malformed models and changed XML sidecars are refused.

The configured Pandoc `--sandbox` uses PandocPure for named document inputs;
fixed arguments exclude filters and other execution paths. Each actual reader
and core process is resource-limited. This document IO isolation does not claim
an OS namespace. See [the executed reader gap](pandoc-gap.md) for a mixed-run
text-loss regression also reproduced with official Pandoc 3.12.1.

PDF extraction has not been routed through Pandoc or Poppler. Poppler remains
an unrun comparison implementation, not a hidden production substitute.
Independent synthetic PDF rendering and geometry comparison are NOT_RUN.

Consequently PDF inputs fail closed as PdfReaderNotQualified. ZIP candidates
must pass DOCX package inspection and model/source validation. The application does not
mislabel those documents as image-only, encrypted, malformed or OCR-qualified;
the required NeedsTextRecognition and mixed-page outcomes remain NOT_IMPLEMENTED.

The acquisition and initial comparison requirements above have now executed.
Next required PDF boundary: repair the demonstrated decoding/geometry losses,
complete the selected reader's page observations, and qualify its bounded
non-networked process before enabling decoding. DOCX's bounded
Pandoc-plus-source-sidecar path is implemented; the identified mixed-run bug
provides a concrete reason for a focused Pandoc reader patch.
